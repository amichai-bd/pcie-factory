# pcie_pcs 8b/10b code

The transmission code of the [`pcs` HAS](HAS.md), written out in full so
the encoder, the decoder and their tests can be built from this page alone
(decision Q21 in the [M1 epic](https://github.com/amichai-bd/pcie-factory/issues/65)).
It is the classic 8b/10b code that the Base Spec uses at 2.5 GT/s; the
citations point there for cross-checking only
[cite: PCIe Base Spec, rev 3.0, §4.2.1.1]. The
[architecture model](../../../../src/arch/pcs/pcie_pcs_8b10b.py) computes
every code from the rules below, and its self-tests check the properties
listed at the end.

## Names and bit order

- A byte `HGFEDCBA` (`H` most significant) splits into `x = EDCBA` (0 to
  31) and `y = HGF` (0 to 7). It is named `Dx.y` as data and `Kx.y` as a
  K (control) symbol.
- A symbol is ten bits named `a b c d e i f g h j` in line order: `a` is
  sent first. On the [symbol interface](HAS.md#interfaces), `a` is bit 0 of
  each 10-bit field. Here codes are written in line order, `a` leftmost.
- The code is two sub-blocks: six bits `abcdei` from `x`, then four bits
  `fghj` from `y`.

## Running disparity

The running disparity (RD) is either negative or positive. It is updated
after each sub-block:

- a sub-block with more ones than zeros, or exactly `000111` (six bits) or
  `0011` (four bits), leaves RD positive;
- a sub-block with fewer ones than zeros, or exactly `111000` or `1100`,
  leaves RD negative;
- any other sub-block (balanced) leaves RD unchanged.

The 6b sub-block is chosen from the RD before the symbol and the 4b
sub-block from the RD after the 6b sub-block. Every sub-block the encoder
sends either is balanced, or has disparity +2 when RD was negative, or -2
when RD was positive; so RD alternates and the line stays DC balanced.

## Encoder: 6b sub-block

The rule is given for RD negative ("RD- form"). The RD+ form is the
complement of the RD- form when that form is unbalanced or is `111000`;
otherwise the two forms are the same.

- **Rule.** If `EDCBA` holds two or three ones (and `x` is not 24), send
  `A B C D E` as `a b c d e`, and set `i` to 1 when there are two ones and
  to 0 when there are three. Example: D5 (`EDCBA` = 00101) sends `101001`.
  D7 sends `111000` (RD+ form `000111`).
- **Exceptions.** Every other `x` (none, one, four or five ones) and D24
  use a fixed RD- form, each with four ones:

  | `x` | RD- form | `x` | RD- form | `x` | RD- form |
  | --- | --- | --- | --- | --- | --- |
  | 0 | `100111` | 15 | `010111` | 27 | `110110` |
  | 1 | `011101` | 16 | `011011` | 29 | `101110` |
  | 2 | `101101` | 23 | `111010` | 30 | `011110` |
  | 4 | `110101` | 24 | `110011` | 31 | `101011` |
  | 8 | `111001` | | | | |

- **K28** uses `001111` (RD+ form `110000`), the only 6b block that can
  start a comma.

## Encoder: 4b sub-block

Again for RD negative (here the RD after the 6b sub-block), with the RD+
form the complement of an unbalanced form or of `1100`:

| `y` | RD- form | Rule |
| --- | --- | --- |
| 0 | `1011` | fixed |
| 1, 2, 5, 6 | `F G H` then `j` = 1 for one one, 0 for two | balanced: `1001`, `0101`, `1010`, `0110` |
| 3 | `1100` | `F G H` then 0; RD+ form `0011` |
| 4 | `1101` | fixed; RD+ form `0010` |
| 7, primary (P7) | `1110` | RD+ form `0001` |
| 7, alternate (A7) | `0111` | RD+ form `1000` |

**A7 rule.** `Dx.7` uses A7 exactly when P7 would make five equal bits in a
row across `e i f g h`: when `e` and `i` are both 1 and P7 starts `111`, or
both 0 and P7 starts `000`. That happens for D17, D18 and D20 at RD
negative and for D11, D13 and D14 at RD positive. Every `Kx.7` uses A7.

## K symbols

The valid K symbols are K28.0 to K28.7, K23.7, K27.7, K29.7 and K30.7.

- `Kx.7` for x in 23, 27, 29, 30: the data 6b sub-block of `x`, then A7.
- `K28.y`: at RD negative, `001111` then the RD+ form of the 4b sub-block
  of `y` (A7 for y = 7); at RD positive, the complement of that whole
  code. Example: K28.5 is `0011111010` and `1100000101`.

This design uses: COM K28.5 (`0xBC`), SKP K28.0 (`0x1C`), FTS K28.1
(`0x3C`), SDP K28.2 (`0x5C`), IDL K28.3 (`0x7C`), PAD K23.7 (`0xF7`), STP
K27.7 (`0xFB`), END K29.7 (`0xFD`) and EDB K30.7 (`0xFE`)
[cite: PCIe Base Spec, rev 3.0, §4.2.1.1]. The encoder encodes all 12
valid K codes above as given; a K flag on a byte that is not one of them is
sent as EDB. K28.7 is EIE, used only in the electrical idle exit ordered set
at 5 GT/s, so this Gen1 design never sends it: the MAC does not ask for it. It is the one
symbol that can put a comma off the symbol boundary (see below). While
locked, the aligner already ignores off-boundary commas; Gen2 work must
also keep hunting from locking onto them.

## Decoder and error classes

A received code is looked up at the current RD:

| Class | Condition | Output |
| --- | --- | --- |
| Valid | The code is the encoder's output for some byte at this RD. | The byte and its K flag. |
| Disparity error | Not valid at this RD, but valid at the other RD. | The byte and its K flag. |
| Code error | Valid at neither RD (includes any code with other than four, five or six ones). | EDB as a K symbol. |

After every received code, valid or not, RD is updated from its two
sub-blocks by the [running disparity](#running-disparity) rule. For the
first symbol after symbol lock, and after RxPolarity changes, RD is
unknown and either column is accepted. RxPolarity changes when its value
differs between two consecutive `clk_i` cycles, whether or not a word was
received in either. With RD unknown, the RD before the symbol, from which
the RD after it is computed, is taken as negative unless the code is valid
only at positive RD (a code valid at neither RD also starts from negative),
which is the architecture model's `decode()`. A single flipped bit always
changes a code's disparity by two, so it shows up as a code error or a
disparity error at that symbol or at a later one.

## Comma

A **comma** is the seven bits `0011111` or `1100000` in line order. In the
codes above it occurs only as bits `a` to `g` of K28.1, K28.5 and K28.7,
and, apart from sequences that include K28.7, never across a symbol
boundary. Finding it therefore gives the symbol boundary; the aligner uses
it ([receive path](RECEIVE.md#comma-alignment-and-symbol-lock)). Because the
two comma forms are each other's complement, as are the two forms of COM
and SKP, comma detection and COM and SKP matching do not depend on lane
polarity.

## Checked properties

The model's `code_properties` scenario and self-tests check, exhaustively:
every symbol round-trips at both RD values; the codes at one RD are
distinct; every code holds four, five or six ones as RD allows; no
sequence of two symbols has a run of more than five equal bits; commas
occur only as described above; SKP and COM are complements across columns
and SKP leaves RD unchanged (so adding or removing one never disturbs the
decoder). Five widely published anchor values (K28.5, K28.0, D21.5, D10.2,
D0.0) are compared bit for bit.
